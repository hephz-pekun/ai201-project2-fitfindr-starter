## Tool Inventory

### `search_listings(description, size=None, max_price=None) -> list[dict]`

#### Inputs

- `description` (str): Keywords describing what the user is looking for.
- `size` (str | None): Optional size filter.
- `max_price` (float | None): Optional maximum price filter.

#### Returns

- A list of matching listing dictionaries sorted by relevance.
- Returns an empty list if no matching items are found.

---

### `suggest_outfit(new_item, wardrobe) -> str`

#### Inputs

- `new_item` (dict): Selected item from the search results.
- `wardrobe` (dict): User wardrobe containing clothing items.

#### Returns

- A non-empty string containing outfit recommendations and styling advice.
- If the wardrobe is empty, returns general styling suggestions instead of outfit combinations.

---

### `create_fit_card(outfit, new_item) -> str`

#### Inputs

- `outfit` (str): Outfit recommendation generated by `suggest_outfit`.
- `new_item` (dict): Selected item information.

#### Returns

- A social-media-style outfit caption describing the item, styling choices, and overall vibe.
- Returns an error message string if the outfit input is empty.

## Planning Loop

The agent begins by parsing the user's query into a description, size, and maximum price. It then calls search_listings() and stores the results in the session. If no results are found, an error message is stored and the agent returns early. Otherwise, the top result is selected and passed to suggest_outfit(). The resulting outfit suggestion is then passed to create_fit_card(). The completed session is returned to the user interface.

## State Management

FitFindr uses a session dictionary to maintain state throughout a user interaction. The session acts as the single source of truth and stores all information generated during the planning loop.

At the beginning of each interaction, the agent creates a new session containing the user's query, parsed search parameters, search results, selected item, wardrobe data, outfit suggestion, fit card, and any error message.

As the agent progresses through the workflow, data produced by one tool is stored in the session and reused by later tools:

1. The parsed query is stored in `session["parsed"]`.
2. Results returned by `search_listings()` are stored in `session["search_results"]`.
3. The highest-ranked result is saved as `session["selected_item"]`.
4. The selected item is passed to `suggest_outfit()`, and the response is stored in `session["outfit_suggestion"]`.
5. The outfit suggestion and selected item are then passed to `create_fit_card()`, and the generated caption is stored in `session["fit_card"]`.

This approach allows information to flow between tools without requiring the user to re-enter data. For example, the item selected by `search_listings()` automatically becomes the input for `suggest_outfit()`, and the resulting outfit recommendation automatically becomes the input for `create_fit_card()`. If any step fails, an error message is stored in `session["error"]` and the agent can stop early while preserving the state needed for debugging and user feedback.

- Selected listing from search results

**Tool:** `create_fit_card`

**Input:**

- Outfit suggestion from Step 2

**Why this tool:**

**Output:**

A completed fit card describing the outfit and overall aesthetic.

- Top listing recommendation
- Outfit suggestion generated from the wardrobe
- Social-media-style fit card summarizing the look

## Error Handling and Fail Points

| Tool | Failure Mode | Agent Response |
|--------|--------|--------|
| `search_listings` | No results match the query | Returns an empty list. The planning loop sets an error message and terminates the interaction early. |
| `search_listings` | Missing or incomplete filter information | Continues searching using the available parameters. |
| `suggest_outfit` | Wardrobe is empty | Generates general styling advice for the selected item instead of specific outfit combinations. |
| `suggest_outfit` | No compatible wardrobe items found | Recommends styling the selected item on its own and suggests complementary pieces. |
| `create_fit_card` | Outfit input is empty or missing | Returns a descriptive error message instead of calling the LLM. |

## Spec Reflection

### One way planning.md helped during implementation

Planning.md provided a clear blueprint for the project before implementation began. The planning loop, state management section, and architecture diagram helped define how data would move between tools and made it easier to implement and debug the agent workflow. Having the error handling documented beforehand also made it easier to build and test failure cases.

### One divergence from your spec, and why

My original specification included additional tools called `rank_listings` and `validate_budget`. During implementation, I simplified the design to use only the three required tools from the project starter code. Relevance scoring was incorporated directly into `search_listings`, and budget validation was handled through the existing search filters. This reduced complexity while still meeting all project requirements.
